# Database schema

Eight tables. This document explains what each one is *for* and why it is shaped
the way it is; the authoritative definition is the SQLAlchemy models under
[backend/app/db/models/](../backend/app/db/models/) and the migrations under
[backend/alembic/versions/](../backend/alembic/versions/).

## Shape of the whole thing

```
users
  └── repositories                (owner_id, CASCADE)
        ├── code_chunks           (repository_id, CASCADE)     -- pgvector
        ├── webhook_events        (repository_id, SET NULL)
        └── pull_requests         (repository_id, CASCADE)
              └── review_jobs     (pull_request_id, CASCADE)
                    └── reviews   (review_job_id, CASCADE)  1:1
                          └── findings  (review_id, CASCADE)
```

Read it as the life of one review: a **user** connects a **repository**; GitHub
sends a **webhook event**; that event concerns a **pull request**; DevPilot
creates a **review job** to look at it; the job produces one **review**; the
review contains many **findings**. **Code chunks** sit off to the side — they are
the indexed repository content that retrieval searches.

## Conventions applied to every table

**UUID primary keys, not auto-incrementing integers.** Ids appear in URLs and in
webhook payloads. Sequential integers leak how many rows exist and let anyone
enumerate other users' resources by subtracting one. UUIDs are also generated by
the application, so a row's id is known before it is inserted — which is what
lets the pipeline build relationships without round-tripping to the database for
each one. Stored as `CHAR(32)` (hex, no dashes) rather than Postgres `uuid`, so
the same models run against SQLite in tests.

**`created_at` / `updated_at` on everything**, set by the application rather than
by a database default. One clock, one code path, and the values are identical in
tests and in production.

**`ON DELETE CASCADE` in the database, with `passive_deletes=True` on the ORM
relationship.** Without the ORM flag, SQLAlchemy dutifully loads every child row
and deletes them one at a time before deleting the parent — N+1 statements to do
what the database was already going to do in one. The cascade rules also mean
deleting a user genuinely removes their data, rather than leaving orphans behind
that no code path will ever look at again.

**Enum-like columns are `VARCHAR` with a Python `Enum`**, not Postgres `ENUM`
types. Adding a value to a Postgres enum requires a migration and, historically,
could not run inside a transaction. A string column plus a validated Python enum
gives the same safety at the boundary with none of the migration pain.

## users

Accounts. `email` is unique and indexed; `hashed_password` holds an **Argon2id**
hash, never anything reversible.

`github_id` and `github_login` are nullable because a DevPilot account exists
before it is linked to GitHub, and can be unlinked afterwards. `github_id` is
uniquely indexed: one GitHub identity maps to at most one DevPilot account, which
is what stops a second account from claiming an identity someone already linked.
The **numeric id** is the identity, not the login — GitHub logins can be renamed
and reused, ids cannot.

## repositories

Repositories a user has chosen to track.

The important constraint is `uq_repositories_owner_id_github_repo_id`: unique on
**(owner_id, github_repo_id)**, not on `github_repo_id` alone. Two users can both
track the same repository, which is ordinary and which the original global
constraint made impossible — silently, with an empty dashboard rather than an
error. See tradeoff 72; migration `0006`.

`installation_id` is the GitHub App installation that grants access. It is
nullable because a repository row can exist from an OAuth-scoped listing before
the App is installed on it.

`indexed_at` and `indexed_commit_sha` record what the `code_chunks` for this
repository actually represent, so a re-index can tell whether there is anything
to do.

## code_chunks

Indexed repository content for retrieval. This is the only table that needs the
`vector` extension.

`embedding` is `VECTOR(1024)`, matching `voyage-code-3`. The dimension is fixed
in the column type on purpose: vectors from two different models are not
comparable, so a mismatch must fail at insert time rather than quietly return
nonsense distances. Changing models means a migration and a full re-index.

`file_path`, `start_line` and `end_line` are stored with every chunk so a
retrieved snippet can be cited by location rather than presented as anonymous
text. Two `CHECK` constraints keep those honest: `start_line > 0` and
`end_line >= start_line`.

`content_hash` is the deduplication key. `uq_code_chunks_identity` is unique on
**(repository_id, file_path, content_hash)**, so re-indexing an unchanged file
inserts nothing and costs no embedding calls. Chunks whose hash no longer appears
in the file are deleted, which is what stops the table from accumulating every
version of every function ever written.

The vector index is created in migration `0004`:

```sql
CREATE INDEX ix_code_chunks_embedding_hnsw
    ON code_chunks USING hnsw (embedding vector_cosine_ops);
```

**HNSW, not IVFFlat** — IVFFlat computes its centroids from existing rows at
build time, so an index built by a migration on an empty table is worthless until
rebuilt. And the operator class must match the distance operator the query uses,
or the planner silently ignores the index and sequentially scans. See tradeoff
64.

## pull_requests

Pull requests DevPilot knows about, one row per pull request, updated in place as
GitHub reports new pushes.

Two unique constraints, both scoped to the repository:
`uq_pull_requests_repository_id_github_pr_id` and
`uq_pull_requests_repository_id_number`. The first was originally global, with
exactly the failure mode described under `repositories` — see tradeoff 73 and
migration `0007`.

`head_sha` is what makes a review reproducible. A review is *about a commit*, not
about a pull request: the branch moves, and a comment pinned to the wrong commit
lands on a line that no longer exists.

## webhook_events

Every delivery GitHub makes, stored before anything is done with it.

`delivery_id` carries a **unique index**, and that index is the entire
idempotency mechanism. GitHub redelivers anything it believes failed, so the
second delivery of the same event must do nothing. The code inserts and catches
`IntegrityError` rather than checking first — a check-then-insert is two
statements with a race between them, and the unique index is the only check that
is actually atomic.

`payload` is the raw JSON, kept whole. It is the only record of what GitHub
actually sent, which is the difference between debugging a bad delivery and
guessing about it. `status` and `error_message` record what happened, so a failed
delivery is a queryable row rather than a log line that has aged out.

`repository_id` is `ON DELETE SET NULL`, not `CASCADE`: the audit trail of what
arrived should outlive the repository it referred to.

## review_jobs

One attempt to review one commit of one pull request. This is the unit of work
Celery consumes.

`status` moves `queued -> running -> completed | failed`. Claiming a job is a
**conditional update** (`... WHERE status = 'queued'`) rather than a read followed
by a write: under redelivery two workers really do receive the same job, and only
the one whose `UPDATE` reports a row is allowed to proceed.

`attempts` and `max_attempts` bound retrying in the database rather than only in
Celery's own retry state, so the count survives a broker that lost its messages.

`error_type`, `error_message` and `error_traceback` are stored on failure. A
failed job that leaves no record is a job nobody can diagnose — this is the
"store failed jobs" requirement, and it is the reason the dashboard can show
*why* something failed rather than just that it did.

`celery_task_id` is indexed so a task id from a log line can be traced back to
the row it was working on.

## reviews

The result of a successful job. **One review per job**, enforced by
`uq_reviews_review_job_id` — a job that somehow ran twice cannot produce two
reviews.

`risk_score` is an `INTEGER` with a `CHECK` constraint pinning it to 0–100. It is
computed in [`app/services/risk.py`](../backend/app/services/risk.py) from the
severities of the findings, **never chosen by the model**. That is the single
most important design decision in the project: a number the model picks is not
comparable between two reviews, cannot be explained, and drifts when the model or
the prompt changes. A deterministic function of the findings can be recomputed,
unit-tested, and defended.

`model_name`, `prompt_tokens` and `completion_tokens` record what a review cost
and which model produced it. Without them, "did the new model make reviews worse"
is unanswerable.

`github_review_id` is written after a successful post and is the post-once
marker: a review that already has one is never posted again, which is what stops
a redelivered job from stacking duplicate reviews on someone's pull request.

## findings

Individual issues. Each has a `category` (indexed), a `severity` (indexed —
severity is what the dashboard filters and sorts on), a `file_path`, and an
optional `line`.

`line` is nullable because a finding can legitimately be about a whole file, and
a `CHECK` keeps it positive when present. `confidence` is a float with a `CHECK`
constraining it to 0.0–1.0.

`is_posted` and `github_comment_id` distinguish **stored** from **published**.
Findings below the confidence threshold are kept and shown on the dashboard but
never posted to GitHub — the cost of a weak finding is far higher on a public
pull request than in a list the user chose to open. See tradeoff 69.

## Migrations

| Revision | What it does |
|---|---|
| `0001` | The seven core tables |
| `0002` | `CREATE EXTENSION vector` and `code_chunks` |
| `0003` | `users.github_id` / `github_login` |
| `0004` | Widens `embedding` to 1024 dimensions and adds the HNSW index |
| `0005` | `reviews.github_review_id` |
| `0006` | Repository identity scoped to the owner |
| `0007` | Pull request identity scoped to the repository |

Every migration implements `downgrade()`. A migration you cannot reverse is a
deploy you cannot roll back.

`backend/tests/test_migrations.py` renders the whole chain offline
(`alembic upgrade head --sql`) and compares the result against the model
metadata, so a model changed without a migration fails the test suite instead of
failing a deploy.
